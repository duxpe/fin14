# fin14 — Product Requirements Document

**Version:** 0.12.0  
**Status:** Draft  
**Date:** 2026-06-05  

---

## 1. Overview

fin14 is a budget CLI for static sites. The core principle is the **14kB per page** limit — a practical heuristic derived from TCP slow start and the initial congestion window described in RFC 6928. Pages that fit within this limit tend to respect a payload envelope small enough to avoid extra round-trips in many scenarios, but the value is not a universal network guarantee.

fin14 is **SSG-agnostic**. It operates on already-generated output — `dist/`, `_site/`, `public/`, or any output directory — and produces a static, deterministic, reproducible estimate of the compressed payload for first-visit resources. It works with Hugo, Eleventy, Astro, Jekyll, or any tool that produces static HTML.

The name comes from `Finch` and `14kB`. `fin14` is also the main CLI command. fin14 is part of a larger ecosystem:

| Product | Name | Purpose |
|---|---|---|
| Budget tool | **fin14** | Estimates and validates the weight of any static site |
| Opinionated SSG | **the14** | Static site generator built on top of fin14 |
| CMS | **sam14** | Content management interface integrated with the14 |

This PRD covers **fin14** exclusively.

### 1.1 Implementation Baseline

Version 0.12.0 builds on the 0.11.0 as-built baseline and adds the first three capabilities that were previously deferred as out of scope: **page include/exclude globs**, **per-page budget overrides**, and a distinct **exit code 2** for configuration/tool errors. It also adds per-SSG usage recipes (documentation only). Everything else preserves the 0.11.0 contract.

These changes stay inside the product's principles: fin14 still only measures (never transforms), keeps zero runtime dependencies for the new glob matcher (in-house, no library), and remains SSG-agnostic and deterministic.

0.12.0 also adds the machine/CI surface that builds on the same measurement core, without touching it: `--json` machine-readable output, GitHub workflow annotations plus a composite GitHub Action, and a `--baseline` regression comparison. These are CLI-layer reporters over the existing `SiteSummary`; `@fin14/core` is unchanged.

The current npm packages are `@fin14/core@0.1.0` and `fin14@0.1.0`. PRD versions track product documentation history and are intentionally independent from npm package release versions.

## 2. Goals

- Make it trivial to verify whether static pages fit within 14kB
- Work with any SSG without tool-specific configuration
- Provide real-time budget visibility during development
- Be simple enough for any developer to get started in under 5 minutes
- Be useful in CI as a weight linter — fail the pipeline if any page exceeds budget

---

## 3. Design Pillars

### 3.1 Agnostic by principle

fin14 does not know — and does not need to know — how the site was built. It reads HTML, CSS, JS, and image files from an output folder and estimates the budget. Any SSG that generates static files is compatible by default.

### 3.2 Honest measurement

fin14 produces a deterministic compressed estimate: HTML, declared static resources, included external resources, and eager/visible images per documented heuristic. There are no automatic optimizations that mask size — the reported number is reproducible and comparable across machines, but does not claim to replace actual measurement from a server, CDN, browser, or network.

### 3.3 Immediate and visual feedback

Budget feedback must be immediate and clear, both in the terminal (TUI) and on the browser report page. The user does not need to understand TCP slow start to understand "9.2 / 14.0 kB ✓".

### 3.4 Real and explainable problem

fin14 addresses a concrete technical problem in a way that any developer can explain in one sentence.

## 5. System Architecture

### 5.1 Repository Structure (monorepo)

```
fin14/
├── package.json                        ← npm workspaces config
├── action.yml                          ← composite GitHub Action (runs npx fin14)
├── packages/
│   ├── core/                           ← @fin14/core
│   │   ├── package.json
│   │   └── src/
│   │       ├── budget/
│   │       │   ├── collector.js        ← parses HTML, resolves which resources enter the budget
│   │       │   ├── measurer.js         ← compresses and measures any resource (local or external)
│   │       │   ├── external.js         ← fetch + cache of external resources
│   │       │   └── validator.js        ← aggregates measurements, applies limit, generates diagnosis
│   │       ├── crawler.js              ← scans output dir, lists HTML files
│   │       ├── compress.js             ← gzip/brotli, bytes in/out
│   │       ├── glob.js                 ← zero-dep glob matcher + page filter + per-page budget resolution
│   │       └── index.js                ← core public API
│   └── cli/                            ← fin14 (npm published package)
│       ├── package.json
│       ├── bin/
│       │   └── fin14.js                ← entry point, argv parsing
│       ├── commands/
│       │   ├── default.js              ← default command: orchestrates crawler + budget + output
│       │   ├── dev.js                  ← pure dev mode orchestrator
│       │   ├── audit.js                ← single page budget + detailed output
│       │   └── reporters.js            ← JSON report, GitHub annotations, baseline diff (pure)
│       └── dev-server/
│           ├── watcher.js              ← Chokidar, emits change events
│           ├── server.js               ← HTTP + serves report-ui/
│           ├── sse.js                  ← manages SSE connections and broadcast
│           └── report-ui/
│               └── index.html          ← report page (static file in package)
```

**Module responsibilities:**

`budget/collector.js` — uses parse5 to parse HTML via manual traversal (`walk()` function). Extracts the v1 resource matrix: `<link rel="stylesheet">`, `<style>`, `<script>` with `src`, `<img src>`, fallback `src` within `<picture>`, `<link rel="preload">`, `<link rel="modulepreload">`, and absolute URLs. Inline CSS and JS bytes are counted as part of compressed HTML; inline CSS is still parsed for local `@import` and `@font-face` discovery. For each critical CSS found, uses `css-tree` to collect recursive local `@import`, detect cycles via a `Set` of visited paths, and add font URLs declared in `@font-face` — **only the first `src:` entry per `@font-face` rule** (alternate formats are skipped; see D41). External CSS `@import` is outside the implemented v1 matrix. After collecting all resource references, deduplicates by resolved key (absolute filesystem path for local, full URL for external with hash stripped); first-occurrence category wins (see D42).

`budget/measurer.js` — receives a resource (local or external) and returns its compressed size in bytes. Delegates disk reading to the caller, fetch to `external.js`, and compression to `compress.js`.

`budget/external.js` — fetches external resources with disk cache (`.fin14/cache/` under the current working directory). 1h TTL. Expired entries are refetched without a dedicated expiry warning in the current implementation. Fetches use 5s timeout and up to 5 redirects by default, limited to 10 simultaneous requests per domain via simple semaphore (Map of counters per hostname). The downloaded body is recompressed locally using the same configuration as local resources.

`budget/validator.js` — receives the list of measurements for a page, sums, resolves the page's limit via `glob.js#resolveBudget` (`budget.overrides` first-match, else `budget.default`), compares, and returns the result with a diagnostic of cut candidates. Suppresses the E13 IPv6 warning when an override applies (D58).

`crawler.js` — recursively scans the output dir and returns the list of HTML files found. Has no budget logic and no filtering; `include`/`exclude` filtering is applied separately by `measureSite` via `glob.js#filterPages`.

`glob.js` — pure, zero-dependency. `matchGlob(path, pattern)` (anchored `*`/`**`/`?` match), `filterPages(relPaths, config)` (apply `project.include`/`project.exclude`), and `resolveBudget(relFile, config)` (per-page budget). No I/O.

`compress.js` — pure function: receives bytes and compression config, returns compressed bytes. No I/O.

`dev-server/server.js` — HTTP server that serves the static files from `report-ui/`. It binds to `127.0.0.1` and tries ports 4214 through 4223. Does not interfere with the SSG server.

`dev-server/sse.js` — manages SSE connections opened by the report page and broadcasts updated measurement data when the watcher detects changes.

### 5.3 Configuration (`fin14.toml`)

```toml
[project]
output_dir    = "dist"            # SSG output folder
build_command = "npm run build"   # command to rebuild (optional)
include       = []                # glob allow-list of pages (optional; empty = all HTML)
exclude       = ["404.html"]      # globs to skip (optional)

[budget]
default                = "14kb"   # default limit for all pages
compression            = "gzip"   # options: "gzip" (default), "brotli"
compression_level      = 6        # 1–9, gzip only (default: 6)
cut_candidate_min_bytes = 2800    # resources below this byte count show no cut hint (default: 2800)
baseline_min_delta_bytes = 100    # baseline deltas below this byte count are hidden (default: 100)

[[budget.overrides]]              # per-page budgets (optional; first match wins)
path   = "gallery/**/*.html"
budget = "50kb"

[network]
timeout_ms    = 5000              # timeout for external resources
max_redirects = 5                 # maximum redirects per external fetch

[viewport]
default = "mobile"                # viewport used for lazy image heuristic

[viewport.mobile]
width               = 390
height              = 844
lazy_visible_images = 1

[viewport.desktop]
width               = 1366
height              = 768
lazy_visible_images = 1

[warnings]
exclude = ["E14"]             # suppress specific warnings by code (optional)
```

`output_dir` can be auto-detected if the project contains known SSG config files (see section 6.3).

`budget.default` accepts either an integer byte count or a case-insensitive decimal `"NNkb"` string such as `"14kb"` or `"14.5KB"`. Decimal kB strings are converted to bytes and rounded.

In the core API, `loadConfig()` can return `project.output_dir = null` when no config value or detector result exists. CLI commands convert that unresolved state, missing output directories, and empty HTML output directories into user-facing input errors.

The optional `[warnings]` section accepts an `exclude` array of E-codes (e.g., `["E14"]`). Excluded warnings are fully suppressed: hidden from all output and not evaluated by `--strict`. Internal `Warning` objects are not affected; filtering happens at the display layer in the CLI and dev mode. In dev mode, `state.hiddenWarnings` (a `Set`) is initialized from `config.warnings.exclude` and can be toggled per session without writing back to disk.

`budget.cut_candidate_min_bytes` (default: `2800`) sets the minimum compressed byte count a resource must have to appear in cut candidate hints. Resources below this threshold are silently omitted from the hint list at the display layer (CLI default command, `audit`, and web report side panel). The `cutCandidates` array in `PageResult` is not affected — filtering is purely display-side.

`budget.baseline_min_delta_bytes` (default: `100`) sets the minimum gzipped per-page delta a page must move to appear in a `--baseline` diff (D62). The `--baseline-min-delta <bytes>` flag overrides it for a single run. Both accept a non-negative integer; `0` shows every change.

**Page filtering (`project.include` / `project.exclude`).** Both are optional arrays of globs matched against each page path relative to the output dir. Globs support `*` (within one path segment), `**` (across segments), and `?` (single non-slash character); a pattern is an anchored full-path match. A page is measured when `include` is empty (or matches it) **and** it does not match `exclude`; `exclude` wins over `include`. Filtering is applied after the crawl, inside `measureSite`, so it affects whole-site runs (`fin14 [dir]`, `fin14 audit --all`). An explicitly named single-file audit (`fin14 audit page.html`) is **never** filtered — naming a file is an explicit request to measure it.

**Per-page budgets (`[[budget.overrides]]`).** An optional array of `{ path, budget }` tables. `path` is a glob (same syntax as above); `budget` accepts the same integer-or-`"NNkb"` form as `budget.default`. For each page, the **first** override whose `path` matches sets the limit; pages with no match use `budget.default`. A page covered by an override is exempt from the 12.2 kB IPv6 `--strict` warning (E13) — see D58.

Out of scope for the schema: `base_path`/`public_path`, persistent history, and JavaScript import graph.

### 5.4 Core Public API And Data Contracts

The core package exposes:

```js
loadConfig(options)
measurePage(file, config)
measureSite(outputDir, config, options)
summarize(results, outputDir, siteWarnings)
matchGlob(path, pattern)
filterPages(relPaths, config)
resolveBudget(relFile, config)
```

`measureSite(outputDir, config, options)` accepts progress callbacks used by dev mode:

- `onStart({ total, files })`
- `onPageResult(page, { done, total })`

`ResourceResult.group` is the canonical grouping field for CLI and report semantics. External resources keep their implementation `type` (`css`, `js`, `image`, or `font`) but use `group: "external"`.

`SiteSummary` contains:

```js
{
  outputDir: string,
  generatedAt: string,
  pages: number,
  pass: number,
  warn: number,
  fail: number,
  totalBytes: number,
  topAssets: ResourceResult[],
  siteWarnings: Warning[],
  results: PageResult[]
}
```

If EMFILE occurs during site measurement, fin14 retries with page batch size 10 and emits an E15 entry in `siteWarnings`.

## 6. CLI

### 6.1 Commands

```bash
fin14 [dir]                    # measures and validates output dir budgets (default command)
fin14 dev [dir]                # watch mode with report page and terminal TUI
fin14 audit <file.html>        # detailed report for a specific page
fin14 audit --all [dir]        # detailed report for all pages in output dir
```

`fin14 check [dir]` exists as an alias of the default command for backwards compatibility.

### 6.2 Flags

**Global** — valid for any command:

```bash
--config <path>             # points to an alternative fin14.toml
--verbose                   # detailed output for each step
-h, --help                  # prints usage
```

**Default command and `audit`** — not applicable in `dev`:

```bash
--force                     # continues even with pages over budget (exit code 0)
--strict                    # treats warnings as errors (useful in CI)
--build                     # runs build_command before measuring (one-off override)
```

**Default command only** — not applicable in `audit` or `dev`:

```bash
--json                      # machine-readable JSON report to stdout (suppresses human output)
--baseline <path>           # compare against a previous --json report; print size deltas
--baseline-min-delta <bytes> # minimum gzipped delta shown in the baseline diff (default 100)
--github                    # emit GitHub workflow annotations (auto-enabled in GitHub Actions)
```

`--strict` treats three warning types as errors:

1. **External resource present in budget** — any resource referenced by absolute URL (Google Fonts, CDN, etc.) generates a warning. External means latency outside the project's control.
2. **Page above 12.2kB** — the 12.2kB limit is derived from an IPv6 heuristic based on RFC 8200: 10 × (1280 bytes minimum MTU − 40 bytes IPv6 header − 20 bytes TCP header) = 12,200 bytes. Pages above this value pass the standard 14kB budget but fall outside this conservative envelope.
3. **Unknown budget** — external fetch failure or `build_command` exit code other than zero when old output is available. In normal mode this is a warning; in `--strict` it fails to prevent CI passing with an incomplete measurement.

Warnings excluded via `warnings.exclude` in `fin14.toml` are not evaluated by `--strict`, even when they fall into categories 1–3 above.

When `--build` runs `build_command` and the command fails, fin14 continues measurement if `output_dir` exists, but emits an explicit warning that the result may be using stale output. In `--strict`, this warning becomes an error.

The native argv parser supports `--config=value`, `--baseline=value`, and `--baseline-min-delta=value` (value flags), `--` to end option parsing, `-h`, and `--help`. Unknown options exit with code 2 (see §6.5). `--force`, `--strict`, `--build`, `--json`, `--baseline`, `--baseline-min-delta`, and `--github` are rejected for `fin14 dev`.

### 6.3 Automatic Output Dir Detection

If no `dir` is passed and no `fin14.toml` exists, fin14 tries to infer the output dir from known config files at the project root:

| Detected file | Inferred output dir |
|---|---|
| `hugo.toml` / `hugo.yaml` / `hugo.json` | `public/` |
| `.eleventy.js` / `eleventy.config.js` / `eleventy.config.mjs` / `eleventy.config.cjs` | `_site/` |
| `astro.config.js` / `astro.config.ts` / `astro.config.mjs` / `astro.config.cjs` | `dist/` |
| `_config.yml` / `_config.toml` | `_site/` |
| `next.config.js` / `next.config.ts` / `next.config.mjs` | `out/` (static export only) |
| none detected | error + instruction to create `fin14.toml` |

### 6.4 `fin14 audit` — Output Format

```
  audit  posts/long-post/index.html
  ────────────────────────────────────────────────
  total    16.8 / 14.0 kB   ✗  +2.8kB
  ────────────────────────────────────────────────
  HTML     3.8kB   index.html
  CSS      2.4kB   style.css
  JS       —
  Images  10.6kB   hero.jpg            9.1kB
                   thumb.jpg           1.5kB
  Ext      —
  ────────────────────────────────────────────────
  cut candidates
  → hero.jpg        9.1kB  consider marking as lazy or resizing
  → style.css       2.4kB  CSS looks large; consider purge
```

Formatting rules:

- Types with zero size display `—` (consistent with TUI)
- Each individual resource appears indented under its type
- External resources (Ext) list hostname + size + latency warning
- Cut candidates: for failed pages, resources that cover the overage; for pass/warn pages, the largest optimization candidates. Resources with compressed bytes below `budget.cut_candidate_min_bytes` (default: 2800) are not shown even if they are in `cutCandidates`
- Warning lines in `audit` output include the E-code prefix (e.g., `E14`); E-codes are not shown in the default command, TUI, or web report
- The warning section currently prints strict-failure warnings; default/check output prints all page warnings
- No color by default; ANSI colors when stdout is a TTY

### 6.5 Exit Codes

fin14 distinguishes a budget failure from an operational failure so CI can react differently:

| Code | Meaning |
|---|---|
| `0` | All measured pages pass (or `--force` was used) |
| `1` | A page exceeded its budget, or a `--strict` violation occurred — **measurement ran** |
| `2` | Configuration, input, or tool error — **measurement could not validly run** |

Exit `2` covers: invalid `fin14.toml` (parse error or unknown field), no resolvable output dir, output dir not found, no HTML files found, an unknown CLI option, `--config` missing its argument, a flag rejected for `dev`, `--build` without `build_command`, and `build_command` failing with no usable output. Exit `1` is reserved for the case where fin14 successfully measured the site and found it over budget (or in violation under `--strict`). This lets a pipeline fail on `1` while treating `2` as a setup error to investigate.

### 6.6 Machine-Readable Output & CI Reporters

These features are CLI-layer reporters over the `SiteSummary` from `@fin14/core`; the measurement core is unchanged. They apply to the **default command** only.

**JSON output (`--json`).** Prints a single curated JSON document to stdout and suppresses the human report. Exit codes are unchanged (§6.5). The document is an explicit, stable contract — not a raw dump of internal objects — versioned with `schemaVersion: 1`. Absolute filesystem paths (`resources[].key`/`path`) are stripped so the output is portable and reproducible across machines; resources are identified by `displayPath` (relative to the output dir). Shape:

```jsonc
{
  "schemaVersion": 1,
  "generatedAt": "<ISO timestamp>",
  "outputDir": "dist",
  "pages": 32, "pass": 30, "warn": 1, "fail": 1, "totalBytes": 384210,
  "results": [
    {
      "file": "about/index.html", "status": "fail",
      "totalBytes": 18432, "limitBytes": 14000,
      "overBudget": true, "unknownBudget": false,
      "warnings": [{ "code": "E14", "message": "...", "strictFailure": true }],
      "resources": [{ "group": "html", "type": "html", "displayPath": "about/index.html", "bytes": 7200, "external": false, "inline": true }],
      "cutCandidates": [{ "group": "images", "type": "image", "displayPath": "hero.jpg", "bytes": 9100 }]
    }
  ],
  "topAssets": [/* … */],
  "siteWarnings": [/* … */],
  "baseline": { "pages": [], "added": [], "removed": [] }   // only when --baseline is used
}
```

**GitHub annotations.** When `GITHUB_ACTIONS=true` (or `--github` is passed), fin14 emits workflow commands to stdout in addition to the normal report: `::error file=<dir>/<page>,title=fin14::<page> over budget by X kB (…)` for over-budget pages, and `::warning file=…` for each non-excluded strict warning. These render inline on the pull request. They are **suppressed under `--json`**, which owns stdout.

**Baseline (`--baseline <file.json>`).** Reads a prior `--json` report and compares per-page `totalBytes`. Pages whose absolute delta is at least the threshold (default 100 bytes; `budget.baseline_min_delta_bytes`, overridden per-run by `--baseline-min-delta <bytes>`) are reported as `+`/`-` deltas, plus added/removed page lists. Deltas are measured on the gzipped total, so a small source edit can compress to a sub-threshold change — or to no change at all (gzip works in blocks); `--baseline-min-delta 0` surfaces every change. The comparison is **informational** — it never changes the exit code (the 14 kB limit remains the only gate). A missing or unparseable baseline file is non-fatal: fin14 prints a stderr notice and continues, so the first run before a baseline exists still works. Under `--json`, the diff is embedded as the `baseline` field instead of printed.

## 7. Budget System

### 7.1 What Is Counted

The 14kB budget per page includes a **deterministic v1 resource matrix of first-visit resources**. The matrix is deliberately static: it does not execute JavaScript, does not render layout, and does not attempt to reproduce all browser prioritization decisions.

Included in the calculation:

- Page HTML
- CSS referenced by active `<link rel="stylesheet">`
- Inline CSS and inline JavaScript bytes as part of compressed HTML
- Local CSS files imported by static valid `@import` within critical CSS (recursive)
- First `src:` URL entry declared in `@font-face` rules (alternate formats are skipped; `--verbose` lists them as informational)
- `<script src>` and `type="module"` scripts directly declared in HTML
- `<img src>` without `loading="lazy"`
- Fallback `src` of `<img>` within `<picture>`
- First `loading="lazy"` images in document order, up to `lazy_visible_images` for the active viewport
- `<link rel="preload">` and `<link rel="modulepreload">`
- Absolute external URLs from the items above

Explicitly excluded from the v1 matrix:

- `srcset` alternatives other than the fallback `src`
- JavaScript import graph or transitive module dependencies
- External CSS `@import` URLs
- CSS `background-image`, `mask`, `content`, `cursor`, and other generic `url()` outside `@import` and `@font-face`
- Favicon and `<link rel="icon">`
- CSS deferred via `media="print"` or loaded via JS
- Scripts and resources loaded dynamically via JS

When `--verbose` is active, known resources excluded from the v1 matrix may generate informational warnings without affecting the budget.

### 7.2 Units and URL Resolution

`kB` is decimal. The default limit `14.0 kB` means exactly `14,000 bytes`. Internal calculation always sums and compares bytes; the UI rounds only for display.

URL resolution:

- Relative URL in HTML is resolved relative to the HTML file
- Root-relative URL (`/assets/x.css`) is resolved relative to `output_dir` root
- Relative URL within CSS is resolved relative to the CSS file that declared it
- External resource deduplication keys preserve query strings and strip hashes
- External resource display labels use hostname plus path
- External fetch/cache uses the resource path held by the collector; the current implementation may include the original hash in that fetch path even though the dedup key strips it
- For local disk reads, hash is ignored; query string does not alter the physical path

### 7.3 Measurement

Size is calculated against a **local estimate of compressed payload**, not against actual bytes served by a server or CDN.

**Default algorithm:** gzip level 6 via `zlib`. Brotli is configurable. The choice prioritizes local reproducibility and stable CI comparison; real servers may use different levels, dictionaries, headers, and CDNs.

**Configuration available via `fin14.toml`:**

- `compression` — `"gzip"` (default) or `"brotli"`
- `compression_level` — gzip level 1 to 9 (default: 6); ignored for brotli

Both implementations use native Node.js modules (`zlib.gzipSync` and `zlib.brotliCompressSync`) — zero extra dependencies.

### 7.4 Lazy Image Heuristic

Images without `loading="lazy"` are included in the budget. Images with `loading="lazy"` are included only by order heuristic: fin14 counts the first `lazy_visible_images` lazy images in document order for the active viewport (`mobile` by default).

This rule is conservative and predictable, but does not replace real browser layout. The `loading` attribute is a hint: lazy images within the initial viewport may be loaded during page load, and images outside the viewport may be prioritized differently by the browser.

### 7.5 External Resources

Resources referenced by absolute URL (e.g., Google Fonts, CDNs) are handled as follows:

- fin14 fetches the resource with a 5s timeout and up to 5 redirects
- The downloaded body is recompressed locally using the same configuration as local resources
- The size is added to the page budget
- A warning is emitted identifying the resource and its weight
- The fetch result is cached in `.fin14/cache/` under the current working directory with a 1h TTL
- On expiry, the current implementation refetches without a dedicated expiry warning
- If the fetch fails, the resource is excluded from the sum and the page budget is marked as unknown; in `--strict`, this becomes an error

```
⚠  fonts.googleapis.com/css2?family=Inter  3.1kB  — external resource counted in budget
```

The `.fin14/` directory should be added to the project's `.gitignore`.

### 7.6 Behavior on Budget Overflow

By default, the process exits with code 1 and a diagnostic message:

```
✗  posts/long-post/index.html  exceeded budget: 16.8kB (+2.8kB)

   Cut candidates:
   → hero.jpg                          1.9kB  — consider marking as lazy or resizing
   → fonts.googleapis.com (external)   3.1kB  — consider hosting the font locally
   → style.css                         2.4kB  — CSS looks large; consider purge

   Use --force to ignore this error.
```

fin14 **suggests** optimizations but does not execute them. Fixing is the project's responsibility.

### 7.7 Concurrency Model

fin14 processes pages in **batches of 50** using native `Promise.all` — no p-limit dependency. This stays within macOS file descriptor limits (256 per process) and Linux (1024).

External resource fetches are limited to **10 simultaneous requests per domain**, implemented via a simple semaphore (Map of counters per hostname). No external dependency.

If EMFILE occurs during measurement (error E15), the process automatically retries with a batch of 10 and emits a warning.

### 7.8 Resource Deduplication

The collector resolves all resource URLs to their canonical key before measurement:

- Local resources: absolute filesystem path
- External resources: full URL including query string (hash stripped)

If the same resource appears in multiple categories (e.g., `<link rel="preload" href="hero.jpg">` AND `<img src="hero.jpg">`), it is counted **once** — assigned to the category of its first occurrence in document order. Subsequent occurrences in other categories are silently skipped.

When `--verbose` is active, deduplicated resources are listed:

```
info  hero.jpg already counted as img — skipped preload duplicate
```

## 8. Development Mode (`fin14 dev`)

### 8.1 Features

- Watch output dir with Chokidar — detects when the SSG regenerates files
- Budget report page at `http://localhost:4214` (or the next available port through 4223)
- Terminal TUI with fixed header of global metrics and dynamic activity zone
- Non-TTY line mode for logged terminals
- On-demand rebuild via the `R` key in terminal (runs configured `build_command`)
- Server → browser communication via SSE
- Burst detection: changes within a 300ms window treated as a batch
- Adaptive settle delay to avoid measurements on partial output

### 8.2 Typical Usage Flow

```
Terminal 1: hugo server --watch   (or any SSG in watch mode)
Terminal 2: fin14 dev public/     (fin14 watches the output and measures)

  — user saves a content file
  — SSG detects, rebuilds, updates public/
  — Chokidar detects change in public/
  — fin14 waits for settle delay (adaptive)
  — fin14 re-measures affected pages
  — TUI updates in terminal
  — SSE notifies the report page at localhost:4214
```

Alternatively, with `build_command` configured:

```
Terminal 1: fin14 dev             (fin14 manages the build and watch)

  — user presses R in terminal
  — fin14 runs build_command
  — waits for settle delay and output dir to be updated
  — re-measures and updates TUI and report page via SSE
```

### 8.3 Adaptive Settle Delay

The watcher waits for a stabilization period after the last event before starting measurement. The behavior is **adaptive**:

- **Cold session:** fixed settle delay of 2 seconds until a `build_command` duration has been recorded.
- **After recorded rebuilds:** settle delay = average of recorded `build_command` durations in the session × 0.5. Minimum 200ms, maximum 5s.
- The rolling build-time sample keeps the latest 10 rebuild durations.

The current settle delay is shown in the TUI status line (`settle 340ms`).

**Why not a fixed delay:** SSGs vary widely (Hugo < 100ms; Eleventy with many posts > 1s). A fixed high delay wastes time on fast builds; a fixed low delay produces partial measurements on slow builds.

### 8.4 Report Page (`http://localhost:4214`)

The report page is served by fin14's `dev-server/` on a dedicated port, independent of the SSG server. The server binds to `127.0.0.1`. If port 4214 is busy, it tries 4215 through 4223, then errors if none are available. The chosen port is shown in the TUI:

```
  fin14  dist/  watching
  report  http://localhost:4215  (4214 in use)
```

There is no script injection into the site pages — zero interference with the SSG development flow.

**Budget map (top of page):**

At the top of the page, above the list, a grid of squares represents all pages on the site — inspired by the GitHub contribution graph. Each square is a page. Colors reflect the **effective status** of each page:

- Green — effective status `pass` (including pages whose only warnings are hidden)
- Yellow — effective status `warn`
- Red — effective status `fail` (always red; `fail` cannot be overridden by hiding warnings)

Effective status is computed at display time from the set of visible warnings (`hiddenWarnings` from the current SSE payload). `page.status` in `PageResult` is never mutated. The `cutCandidateMinBytes` value from the SSE payload is used to filter cut candidate hints in the side panel.

Clicking a square smoothly scrolls to the corresponding row in the list below, where the user can click to open the side panel with the full page detail.

**Note:** The color zones reflect effective page status, not strict-mode exit behavior. The conservative 12.2kB threshold (IPv6 heuristic, used by `--strict`) can produce a `warn` page and therefore a yellow square, but `--strict` itself remains a CI concern.

**Page list (overview):**

Each page appears in one row with:
- Visual status icon and color reflecting effective status (✓ pass / ⚠ warning / ✗ fail)
- Current size vs. limit (e.g., `9.2 / 14.0 kB`)

The list is sorted by effective status first (effective-fail, then effective-warn, then effective-pass) and weight second, so violations appear near the top. Summary counters (pass / warn / fail) in the header are recomputed from effective status at display time.

Above the list, three filter tabs — `All`, `Violations + warnings`, `Budget violations only` — narrow the displayed pages (and the budget map) to the matching effective status. The filter is client-side and independent of the TUI's `Shift+Tab` view (D63); `All` is the default and an empty filter shows a `No pages in this view.` placeholder. The header counters always reflect all pages.

**Page detail (side panel):**

Clicking a page opens a side panel with the full breakdown by resource group: HTML / CSS / JS / Images / External. `ResourceResult.group` is the intended grouping contract; external resources are individually identified with their weight and associated warning.

**Updates:**

The page maintains an SSE connection with the server. When the watcher detects a change in the output dir and re-measurement finishes, the server pushes updated data and the page re-renders without a reload.

**Warning configuration panel:**

The report page includes a warning configuration section with one checkbox per warning code. Checking or unchecking a code POSTs to `/warnings/toggle` on the dev server, which updates `state.hiddenWarnings` for the session. SSE payloads include the current `hiddenWarnings` array so the page stays in sync. Excluded warnings are hidden from the page list and detail panel without a full reload. Session-only — resets to the `warnings.exclude` config values on server restart. Warning messages are shown without E-code prefixes; E-codes appear only in the checkbox labels for configuration purposes.

**History:**

Current snapshot only — no history between measurements. The page always reflects the latest state of the output dir.

### 8.5 Terminal TUI

The TUI is composed of a **fixed header** (always visible) and a **dynamic activity zone** (recent pages). The aesthetic follows the pattern of tools like Claude Code and OpenCode: dark background, dense monospaced typography, semantic colors, light separators, footer with available controls.

**Fixed header:**

```
 fin14  dist/  watching    pass 38  warn 3  fail 7   48 pages
 report http://localhost:4214
 ─────────────────────────────────────────────────────────────
 top offenders   style.css 8.4kB · hero.jpg 6.1kB · Inter (ext) 3.1kB
 hint            7 pages failing — style.css looks large, check global CSS
```

When the watcher is waiting for the settle delay:

```
 fin14  dist/  settling    pass 38  warn 3  fail 7   48 pages
 report http://localhost:4214    settle 340ms
 ─────────────────────────────────────────────────────────────
 top offenders   style.css 8.4kB · hero.jpg 6.1kB · Inter (ext) 3.1kB
 hint            updating 12 files... waiting 340ms
```

- Line 1: tool name, watched output dir, watcher status, global counters (`pass N warn N fail N`), total pages
- Line 2: report URL and a persistent `view: <label>` badge showing the active list view (`all pages` / `violations + warnings` / `budget violations only`) once a measurement exists
- Line 3: separator
- Line 4: the 3 heaviest assets across the entire site (not a specific page), with individual sizes
- Line 5: dynamically generated text hint — examples: "7 pages failing — style.css looks large, check global CSS"; "external resource Inter is 3.1kB — consider hosting locally"; "all pages within budget"

**Activity zone (dynamic):**

Lists pages one per line. Resource types with zero weight are omitted. Rows sort by status first (`fail`, then `warn`, then `pass`) and weight second. After watcher batches, changed paths are prioritized before the status/weight sort. The number of lines displayed is calculated dynamically from terminal height.

```
 recent
 ✗  posts/long-post           16.8 / 14.0 kB  +2.8  HTML 3.8  CSS 2.4  Imgs 10.6
 ✓  posts/index                9.2 / 14.0 kB        HTML 4.1  CSS 2.8  Imgs 2.3
 ✓  about/index                7.1 / 14.0 kB        HTML 2.9  CSS 4.2
 ─────────────────────────────────────────────────────────────
 R rebuild · Q quit · ↑↓ navigate · Enter detail · F filters · Shift+Tab to switch view
```

When a page is selected with the arrow keys, `Enter` opens a detail view and `Esc` closes it. The detail view shows only the selected page's breakdown — it never carries a rebuild/measure log.

**Transient status band:** after a manual rebuild (`R`) completes, its result shows as a short-lived band just above the footer (`↺ build succeeded (0.3s)`, `✗ build failed (exit 1)`, or `· no build_command configured`). It auto-clears after ~3 s. The band carries only the build outcome — measure counts are omitted because the header already shows pass/warn/fail, so there is no persistent activity log. The band is shown on the pages screen only (never in `detail`/`filters`, nor during an active burst, where the hint already reports progress); a pure file-watch measurement, with no build, shows no band.

Warning messages in the TUI are shown without E-code prefixes. The TUI filters warnings using `state.hiddenWarnings` — warnings excluded via `warnings.exclude` or toggled off via the `F` filters screen (see below) are not shown and do not contribute to the `warn` counter.

Page rows display effective status: if all warnings on a page are hidden, the row shows a green `✓` pass icon. The header counters (pass / warn / fail) are recomputed from effective status at render time. `fail` status (page over budget, E12) is always shown as red and cannot be overridden by hiding warnings.

**Warning filters mode (`F` key):**

Pressing `F` from the `pages` mode switches the TUI to a `filters` mode that lists all 11 excludable warning codes with their descriptions. Navigate with `↑↓`, toggle visibility with `Space`. Changes apply immediately (live). `Esc` exits back to `pages` mode.

```
 fin14  dist/  watching    pass 41  warn 0  fail 7   48 pages
 ─────────────────────────────────────────────────────────────
 warning filters
 ─────────────────────────────────────────────────────────────
   ● E06  CSS file not found — excluded from budget
 > ○ E13  Page exceeds IPv6 heuristic (12.2 kB)
   ● E14  External resource counted in budget
   ...
 ─────────────────────────────────────────────────────────────
 Space toggle · ↑↓ navigate · Esc close
```

`●` = active (visible), `○` = hidden. `>` marks the cursor position. Toggling in the TUI broadcasts the updated `hiddenWarnings` set via SSE, keeping the web report in sync. The `F filters` hint is shown in the footer of all non-filters modes.

Navigation actions (Enter, Esc, arrow keys, F, Space) call `renderNow()`, which bypasses the 50ms debounce and repaints the terminal immediately. Data-driven updates (measurement results arriving from the watcher) continue to use the debounced `render()` to avoid redundant repaints during rapid measurement batches.

In non-TTY mode, `fin14 dev` prints a line with the output dir and report URL, then prints summary lines after measurements instead of rendering the TUI.

### 8.6 Burst Mode (batch update)

When multiple files change within a 300ms window — common in full SSG rebuilds — fin14 enters burst mode. This covers both template edits that affect hundreds of pages and full rebuilds triggered by the SSG itself (which often regenerates the entire site regardless of what changed).

**During the burst**, the header hint becomes a progress bar and the activity zone shows only pages with errors as they are detected:

```
 fin14  dist/  rebuilding        ✓ 38  ⚠ 3  ✗ 7   48 pages
 ─────────────────────────────────────────────────────────────
 top offenders   style.css 8.4kB · hero.jpg 6.1kB · Inter (ext) 3.1kB
 hint            updating 347 pages...  [████████████░░░░]  214 / 347
 ─────────────────────────────────────────────────────────────
 errors found
 ✗  posts/long-post            16.8 / 14.0 kB  +2.8  HTML 3.8  CSS 2.4  Imgs 10.6
 ✗  posts/post-b               15.1 / 14.0 kB  +1.1  HTML 3.2  CSS 2.4  Imgs 9.5
```

**When the burst finishes**, if there are no violations, the TUI returns to the `all pages` view. If there are violations, the view auto-focuses to `violations + warnings` (only non-pass pages). This focus is valuable on large sites; on small ones the hint makes clear the list is filtered and the footer advertises the `Shift+Tab` cycle to widen or narrow it.

**View filter (`Shift+Tab`):** a list view filter cycles forward through three views on `Shift+Tab`:

1. `all pages`
2. `violations + warnings` (effective status `fail` or `warn`)
3. `budget violations only` (effective status `fail`)

The filter is independent of `detail`/`filters` screens and persists across opening and closing a page detail. The active view is shown as a persistent `view: <label>` badge on the header report line (line 2). When the view is not `all pages` the hint line reports the filtered count — `N of M pages` (paginated: `N of M pages — page X/Y ← →`); the `Shift+Tab to switch view` key hint lives in the footer legend. An empty filtered view shows `no pages in this view`.

**Post-burst paginated list:**

When the number of pages in the active view exceeds the available height of the activity zone, the list becomes paginated with `←` `→` navigation:

```
 report http://localhost:4214    view: violations + warnings
 ─────────────────────────────────────────────────────────────
 top offenders   style.css 8.4kB · hero.jpg 6.1kB · Inter (ext) 3.1kB
 hint            89 of 347 pages — page 1/8 ← →
 ─────────────────────────────────────────────────────────────
 ✗  posts/heaviest-post       18.4 / 14.0 kB  +4.4  HTML 3.1  CSS 2.8  Imgs 12.5
 ✗  posts/second-post         17.9 / 14.0 kB  +3.9  HTML 3.8  CSS 2.4  Imgs 11.7
 ⚠  posts/near-limit          13.7 / 14.0 kB        HTML 4.1  CSS 5.2  Imgs 4.4
```

Sort order: status → weight descending; after watcher batches, changed paths are prioritized.

## 9. CI Usage

fin14 is designed to work as a weight linter in CI pipelines:

```yaml
# GitHub Actions example
- name: Build
  run: npm run build

- name: Check page budget
  run: npx fin14 dist/ --strict
```

`--strict` treats as errors: presence of any external resource in budget, pages above 12.2kB (IPv6 heuristic), external fetch failure, and failed `build_command` with stale output available. Exit code 1 on any violation.

Exit codes (see §6.5): `0` all pages pass, `1` budget or `--strict` failure, `2` config/input/tool error. A pipeline can fail on `1` and surface `2` as a misconfiguration to fix rather than a budget regression.

### 9.1 GitHub Action

A composite action (`action.yml` at the repo root, see D61) wraps the CLI for one-line adoption:

```yaml
- uses: duxpe/fin14@v1
  with:
    path: dist        # output dir (default: dist)
    strict: 'true'    # optional
    config: fin14.toml # optional
    version: latest    # optional npm version/dist-tag
```

The Action runs `npx fin14` with the given inputs. Because GitHub sets `GITHUB_ACTIONS=true`, fin14 automatically emits `::error`/`::warning file=…` annotations (§6.6) that render inline on the pull request, and the step fails on exit `1`/`2`.

### 9.2 Baseline in CI

`fin14 dist/ --json > budget-baseline.json` produces a report to commit or cache; a later run with `fin14 dist/ --baseline budget-baseline.json` prints size deltas. The comparison is informational (§6.6); the 14 kB limit is still enforced by the normal run.

## 12. Ecosystem Roadmap

fin14 is the first product of a planned ecosystem. Each phase solves a specific problem and supports the next.

### the14 — Opinionated SSG

Static site generator built on top of fin14. While fin14 is agnostic, the14 is deliberately opinionated: it chooses the stack (Markdown, templates, collections) and applies optimizations that fin14 cannot safely do in an agnostic way — such as CSS purge and critical CSS inlining. Every site generated by the14 is born within budget.

Planned scope: Markdown + frontmatter, template engine, native collections (posts, projects, tags), automatic pagination, hot reload with integrated budget overlay, zero JS by default.

### sam14 — CMS

Content management interface integrated with the14. Solves the problem of those who want to maintain a blog or portfolio without editing Markdown files directly. sam14 relies on the14 for building and fin14 for budget validation — the 14kB limit is enforced even through the visual interface.

Planned scope: web content editor, post and project management, real-time preview with visible budget, integrated publishing.

### Hosting platform (future phase)

If the ecosystem gains sufficient adoption, a hosting platform dedicated to sites within the 14kB limit closes the loop: create, measure, publish — all within the same ecosystem. No server configuration, no concern about compression or CDN.

## 13. Success Criteria (fin14 v1)

### 13.1 Testing Strategy

The implementation must have canonical fixtures and stable snapshots before being considered complete:

- Basic HTML below and above 14,000 bytes
- gzip level 6 and brotli
- Valid `@import`, cycle, and missing import
- `@font-face` with local and external font — first `src:` only
- Eager images, lazy by order, `<picture>` with fallback `src`, and ignored `srcset`
- `preload` and `modulepreload`, with deduplication against same-path img/script
- External fetch with success, timeout, redirect, and 404
- `--strict` failing on external resource, unknown budget, page above 12.2kB, and build warning
- Glob matcher units (`*` vs `**`, `?`, anchoring, no false partial match); `filterPages` include/exclude; `resolveBudget` first-match and fallthrough
- `project.include`/`project.exclude` and `[[budget.overrides]]` parsing + E04 on malformed entries
- Exit codes: `0` pass, `1` over budget / `--strict`, `2` config/input/tool error (bad toml, missing dir, unknown flag)
- Reporters: `--json` shape (`schemaVersion`, no absolute paths, valid JSON, exit code preserved), GitHub annotations (`::error`/`::warning`, excluded codes respected), baseline diff (deltas, added/removed, threshold, non-fatal missing file)
- CLI, `audit`, and report UI data snapshots

Acceptance criterion: no section should claim that fin14 measures real network bytes without qualifying the measurement as a deterministic estimate.

### 13.2 Product

- A developer can integrate fin14 into an existing project in under 5 minutes
- fin14 works correctly with Hugo, Eleventy, and Astro without SSG-specific configuration
- The report page updates in under 500ms after the SSG regenerates a file
- `fin14 dist/` on a site with 100 pages ≤14kB completes in under 5 seconds

## Appendix B — Error Taxonomy

### Category A — Input / configuration errors

Exit 2. Clear message. No measurement. (Unknown CLI options, `--config` without an argument, and flags rejected for `dev` also exit 2.)

| ID | Condition | Example message |
|---|---|---|
| E01 | `output_dir` does not exist | `error  dist/ not found` |
| E02 | `output_dir` has no `.html` files | `error  no HTML files found in dist/` |
| E03 | `fin14.toml` invalid (parse error) | `error  fin14.toml: parse error at line 4` |
| E04 | `fin14.toml` with unknown field | `error  fin14.toml: unknown field 'cache_ttl'` |
| E05 | `.html` file passed to `audit` does not exist | `error  file not found: posts/x.html` |

Codes in Category B, C, and D that produce warnings (not hard errors) can be suppressed via `warnings.exclude` in `fin14.toml`. Suppressed warnings are hidden from all output and skipped by `--strict`. Category A codes are input errors and cannot be excluded.

### Category B — Measurement errors

Warning emitted. Process continues. Missing local resources are excluded from budget; external failures mark budget as unknown.

| ID | Condition | Behavior |
|---|---|---|
| E06 | CSS referenced in HTML not found on disk | `warn  style.css not found — excluded from budget` |
| E07 | JS referenced in HTML not found on disk | same |
| E08 | Image or font asset referenced not found on disk | same |
| E09 | External resource fetch failed (timeout / redirect / 4xx / 5xx) | `warn  fonts.googleapis.com: fetch failed — budget unknown`; error in `--strict` |
| E10 | `@import` references a file not found on disk | `warn  @import 'tokens.css' not found — excluded` |
| E11 | Cycle in `@import` (A imports B imports A) | `warn  cycle detected in @import: base.css → tokens.css → base.css` |
| E18 | Known resource outside v1 matrix found in `--verbose` | `warn  background-image in style.css is outside v1 matrix — ignored` |

### Category C — Budget errors

Exit 1 by default. Exit 0 with `--force`.

| ID | Condition | Behavior |
|---|---|---|
| E12 | Page > 14kB | error; exit 1 |
| E13 | Page > 12.2kB and ≤ 14kB | warning; error in `--strict`; **suppressed for pages covered by a `budget.overrides` match** (D58) |
| E14 | External resource present in budget | warning; error in `--strict` |
| E19 | Unknown budget from external fetch or failed build | warning; error in `--strict` |

### Category D — Runtime errors

| ID | Condition | Behavior |
|---|---|---|
| E15 | EMFILE (too many open files) | automatic retry with batch of 10; warning emitted |
| E16 | Port conflict in dev mode | tries `127.0.0.1:4214` through `127.0.0.1:4223`; TUI reports chosen port; errors if range is exhausted |
| E17 | `build_command` failed (exit ≠ 0) | log stderr + continue if `output_dir` exists; marks budget as unknown |
