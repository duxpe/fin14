# fin14 — Product Requirements Document

**Version:** 0.10.0  
**Status:** Implemented Baseline  
**Date:** 2026-05-01  

---

## 1. Overview

fin14 is a budget CLI for static sites. The core principle is the **14kB per page** limit — a practical heuristic derived from TCP slow start and the initial congestion window described in RFC 6928. Pages that fit within this limit tend to respect a payload envelope small enough to avoid extra round-trips in many scenarios, but the value is not a universal network guarantee.

fin14 is **SSG-agnostic**. It operates on already-generated output — `dist/`, `_site/`, `public/`, or any output directory — and produces a static, deterministic, reproducible estimate of the compressed payload for first-visit resources. It works with Hugo, Eleventy, Astro, Jekyll, or any tool that produces static HTML.

The name comes from `Finch` and `14kB`. `fin14` is also the main CLI command. fin14 is part of a larger ecosystem:

| Product | Name | Purpose |
|---|---|---|
| Budget tool | **fin14** | Estimates and validates the weight of any static site |
| Opinionated SSG | **the14** | Static site generator built on top of fin14 |
| CMS | **sam14** | Content management interface integrated with the14 |

This PRD covers **fin14** exclusively.

---

## 2. Goals

- Make it trivial to verify whether static pages fit within 14kB
- Work with any SSG without tool-specific configuration
- Provide real-time budget visibility during development
- Be simple enough for any developer to get started in under 5 minutes
- Be useful in CI as a weight linter — fail the pipeline if any page exceeds budget

---

## 3. Design Pillars

### 3.1 Agnostic by principle

fin14 does not know — and does not need to know — how the site was built. It reads HTML, CSS, JS, and image files from an output folder and estimates the budget. Any SSG that generates static files is compatible by default.

### 3.2 Honest measurement

fin14 produces a deterministic compressed estimate: HTML, declared static resources, included external resources, and eager/visible images per documented heuristic. There are no automatic optimizations that mask size — the reported number is reproducible and comparable across machines, but does not claim to replace actual measurement from a server, CDN, browser, or network.

### 3.3 Immediate and visual feedback

Budget feedback must be immediate and clear, both in the terminal (TUI) and on the browser report page. The user does not need to understand TCP slow start to understand "9.2 / 14.0 kB ✓".

### 3.4 Real and explainable problem

fin14 addresses a concrete technical problem in a way that any developer can explain in one sentence.

## 5. System Architecture

### 5.1 Repository Structure (monorepo)

```
fin14/
├── package.json                        ← npm workspaces config
├── packages/
│   ├── core/                           ← @fin14/core
│   │   ├── package.json
│   │   └── src/
│   │       ├── budget/
│   │       │   ├── collector.js        ← parses HTML, resolves which resources enter the budget
│   │       │   ├── measurer.js         ← compresses and measures any resource (local or external)
│   │       │   ├── external.js         ← fetch + cache of external resources
│   │       │   └── validator.js        ← aggregates measurements, applies limit, generates diagnosis
│   │       ├── crawler.js              ← scans output dir, lists HTML files
│   │       ├── compress.js             ← gzip/brotli, bytes in/out
│   │       └── index.js                ← core public API
│   └── cli/                            ← fin14 (npm published package)
│       ├── package.json
│       ├── bin/
│       │   └── fin14.js                ← entry point, argv parsing
│       ├── commands/
│       │   ├── default.js              ← default command: orchestrates crawler + budget + output
│       │   ├── dev.js                  ← pure dev mode orchestrator
│       │   └── audit.js                ← single page budget + detailed output
│       └── dev-server/
│           ├── watcher.js              ← Chokidar, emits change events
│           ├── server.js               ← HTTP + serves report-ui/
│           ├── sse.js                  ← manages SSE connections and broadcast
│           └── report-ui/
│               └── index.html          ← report page (static file in package)
```

**Module responsibilities:**

`budget/collector.js` — uses parse5 to parse HTML via manual traversal (`walk()` function). Extracts the v1 resource matrix: `<link rel="stylesheet">`, `<style>`, `<script>` inline or with `src`, `<img src>`, fallback `src` within `<picture>`, `<link rel="preload">`, `<link rel="modulepreload">`, and absolute URLs. For each critical CSS found, uses `css-tree` to collect recursive `@import`, detect cycles via a `Set` of visited paths, and add font URLs declared in `@font-face` — **only the first `src:` entry per `@font-face` rule** (alternate formats are skipped; see D41). After collecting all resource references, deduplicates by resolved key (absolute filesystem path for local, full URL for external); first-occurrence category wins (see D42).

`budget/measurer.js` — receives a resource (local or external) and returns its compressed size in bytes. Delegates disk reading to the caller, fetch to `external.js`, and compression to `compress.js`.

`budget/external.js` — fetches external resources with disk cache (`.fin14/cache/`). 1h TTL. On expiry, emits warning and refetches. Fetches use 5s timeout and up to 5 redirects by default, limited to 10 simultaneous requests per domain via simple semaphore (Map of counters per hostname). The downloaded body is recompressed locally using the same configuration as local resources.

`budget/validator.js` — receives the list of measurements for a page, sums, compares against the configured limit, and returns the result with a diagnostic of cut candidates.

`crawler.js` — recursively scans the output dir and returns the list of HTML files found. Has no budget logic.

`compress.js` — pure function: receives bytes and compression config, returns compressed bytes. No I/O.

`dev-server/server.js` — HTTP server that serves the static files from `report-ui/`. If port 4214 is busy, tries 4215, 4216... until a port is available. Does not interfere with the SSG server.

`dev-server/sse.js` — manages SSE connections opened by the report page and broadcasts updated measurement data when the watcher detects changes.

### 5.2 Technology Stack

| Component | Technology | Rationale |
|---|---|---|
| Runtime | Node.js >= 22 (pure ESM) | No transpile in dev, stable `fetch`, npm ecosystem |
| CLI | Native Node.js | No heavy CLI framework dependency |
| File watching | Chokidar | De facto standard for watching in Node.js |
| Compression | Native zlib (Node.js) | Zero extra dependencies; gzip and brotli native |
| Dev server | Native HTTP + SSE | Lightweight, no dependencies, sufficient for this use case |
| Configuration | TOML (`fin14.toml`) | Readable, unambiguous, no JSON quirks |
| HTML parser | parse5 v8 | WHATWG HTML5 spec-compliant; 1 dep (entities); traversal via walk() |
| CSS parser | css-tree | CSS AST parser for `@import`, `@font-face`, and safe resolution of critical URLs |
| TOML parser | smol-toml | Native ESM; TOML 1.1.0 per project repo; 0 deps |

### 5.3 Configuration (`fin14.toml`)

```toml
[project]
output_dir    = "dist"            # SSG output folder
build_command = "npm run build"   # command to rebuild (optional)

[budget]
default           = "14kb"        # default limit for all pages
compression       = "gzip"        # options: "gzip" (default), "brotli"
compression_level = 6             # 1–9, gzip only (default: 6)

[network]
timeout_ms    = 5000              # timeout for external resources
max_redirects = 5                 # maximum redirects per external fetch

[viewport]
default = "mobile"                # viewport used for lazy image heuristic

[viewport.mobile]
width               = 390
height              = 844
lazy_visible_images = 1

[viewport.desktop]
width               = 1366
height              = 768
lazy_visible_images = 1
```

`output_dir` can be auto-detected if the project contains known SSG config files (see section 6.3).

Out of scope for the v1 schema: per-glob or per-page budgets, excludes, `base_path`/`public_path`, persistent history, and JavaScript import graph.

## 6. CLI

### 6.1 Commands

```bash
fin14 [dir]                    # measures and validates output dir budgets (default command)
fin14 dev [dir]                # watch mode with report page and terminal TUI
fin14 audit <file.html>        # detailed report for a specific page
fin14 audit --all [dir]        # detailed report for all pages in output dir
```

`fin14 check [dir]` exists as an alias of the default command for backwards compatibility.

### 6.2 Flags

**Global** — valid for any command:

```bash
--config <path>             # points to an alternative fin14.toml
--verbose                   # detailed output for each step
```

**Default command and `audit`** — not applicable in `dev`:

```bash
--force                     # continues even with pages over budget (exit code 0)
--strict                    # treats warnings as errors (useful in CI)
--build                     # runs build_command before measuring (one-off override)
```

`--strict` treats three warning types as errors:

1. **External resource present in budget** — any resource referenced by absolute URL (Google Fonts, CDN, etc.) generates a warning. External means latency outside the project's control.
2. **Page above 12.2kB** — the 12.2kB limit is derived from an IPv6 heuristic based on RFC 8200: 10 × (1280 bytes minimum MTU − 40 bytes IPv6 header − 20 bytes TCP header) = 12,200 bytes. Pages above this value pass the standard 14kB budget but fall outside this conservative envelope.
3. **Unknown budget** — external fetch failure or `build_command` exit code other than zero when old output is available. In normal mode this is a warning; in `--strict` it fails to prevent CI passing with an incomplete measurement.

When `--build` runs `build_command` and the command fails, fin14 continues measurement if `output_dir` exists, but emits an explicit warning that the result may be using stale output. In `--strict`, this warning becomes an error.

### 6.3 Automatic Output Dir Detection

If no `dir` is passed and no `fin14.toml` exists, fin14 tries to infer the output dir from known config files at the project root:

| Detected file | Inferred output dir |
|---|---|
| `hugo.toml` / `hugo.yaml` | `public/` |
| `eleventy.config.js` / `.eleventy.js` | `_site/` |
| `astro.config.*` | `dist/` |
| `jekyll.yml` / `_config.yml` | `_site/` |
| `next.config.*` | `out/` (static export only) |
| none detected | error + instruction to create `fin14.toml` |

### 6.4 `fin14 audit` — Output Format

```
  audit  posts/long-post/index.html
  ────────────────────────────────────────────────
  total    16.8 / 14.0 kB   ✗  +2.8kB
  ────────────────────────────────────────────────
  HTML     3.8kB   index.html
  CSS      2.4kB   style.css
  JS       —
  Images  10.6kB   hero.jpg            9.1kB
                   thumb.jpg           1.5kB
  Ext      —
  ────────────────────────────────────────────────
  cut candidates
  → hero.jpg        9.1kB  consider marking as lazy or resizing
  → style.css       2.4kB  CSS looks large; consider purge
```

Formatting rules:

- Types with zero size display `—` (consistent with TUI)
- Each individual resource appears indented under its type
- External resources (Ext) list hostname + size + latency warning
- Cut candidates: resources that, if removed or optimized, would resolve the overage
- No color by default; ANSI colors when stdout is a TTY

## 7. Budget System

### 7.1 What Is Counted

The 14kB budget per page includes a **deterministic v1 resource matrix of first-visit resources**. The matrix is deliberately static: it does not execute JavaScript, does not render layout, and does not attempt to reproduce all browser prioritization decisions.

Included in the calculation:

- Page HTML
- CSS referenced by active `<link rel="stylesheet">`
- Inline CSS in `<style>`
- CSS files imported by static valid `@import` within critical CSS (recursive)
- First `src:` URL entry declared in `@font-face` rules (alternate formats are skipped; `--verbose` lists them as informational)
- Inline JavaScript, `<script src>`, and `type="module"` scripts directly declared in HTML
- `<img src>` without `loading="lazy"`
- Fallback `src` of `<img>` within `<picture>`
- First `loading="lazy"` images in document order, up to `lazy_visible_images` for the active viewport
- `<link rel="preload">` and `<link rel="modulepreload">`
- Absolute external URLs from the items above

Explicitly excluded from the v1 matrix:

- `srcset` alternatives other than the fallback `src`
- JavaScript import graph or transitive module dependencies
- CSS `background-image`, `mask`, `content`, `cursor`, and other generic `url()` outside `@import` and `@font-face`
- Favicon and `<link rel="icon">`
- CSS deferred via `media="print"` or loaded via JS
- Scripts and resources loaded dynamically via JS

When `--verbose` is active, known resources excluded from the v1 matrix may generate informational warnings without affecting the budget.

### 7.2 Units and URL Resolution

`kB` is decimal. The default limit `14.0 kB` means exactly `14,000 bytes`. Internal calculation always sums and compares bytes; the UI rounds only for display.

URL resolution:

- Relative URL in HTML is resolved relative to the HTML file
- Root-relative URL (`/assets/x.css`) is resolved relative to `output_dir` root
- Relative URL within CSS is resolved relative to the CSS file that declared it
- Query string and hash are preserved in the cache key for external resources
- For local disk reads, hash is ignored; query string does not alter the physical path

### 7.3 Measurement

Size is calculated against a **local estimate of compressed payload**, not against actual bytes served by a server or CDN.

**Default algorithm:** gzip level 6 via `zlib`. Brotli is configurable. The choice prioritizes local reproducibility and stable CI comparison; real servers may use different levels, dictionaries, headers, and CDNs.

**Configuration available via `fin14.toml`:**

- `compression` — `"gzip"` (default) or `"brotli"`
- `compression_level` — gzip level 1 to 9 (default: 6); ignored for brotli

Both implementations use native Node.js modules (`zlib.gzipSync` and `zlib.brotliCompressSync`) — zero extra dependencies.

### 7.4 Lazy Image Heuristic

Images without `loading="lazy"` are included in the budget. Images with `loading="lazy"` are included only by order heuristic: fin14 counts the first `lazy_visible_images` lazy images in document order for the active viewport (`mobile` by default).

This rule is conservative and predictable, but does not replace real browser layout. The `loading` attribute is a hint: lazy images within the initial viewport may be loaded during page load, and images outside the viewport may be prioritized differently by the browser.

### 7.5 External Resources

Resources referenced by absolute URL (e.g., Google Fonts, CDNs) are handled as follows:

- fin14 fetches the resource with a 5s timeout and up to 5 redirects
- The downloaded body is recompressed locally using the same configuration as local resources
- The size is added to the page budget
- A warning is emitted identifying the resource and its weight
- The fetch result is cached in `.fin14/cache/` with a 1h TTL
- On expiry, a warning is emitted and the fetch is silently redone
- If the fetch fails, the resource is excluded from the sum and the page budget is marked as unknown; in `--strict`, this becomes an error

```
⚠  fonts.googleapis.com/css2?family=Inter  3.1kB  — external resource counted in budget
```

The `.fin14/` directory should be added to the project's `.gitignore`.

### 7.6 Behavior on Budget Overflow

By default, the process exits with code 1 and a diagnostic message:

```
✗  posts/long-post/index.html  exceeded budget: 16.8kB (+2.8kB)

   Cut candidates:
   → hero.jpg                          1.9kB  — consider marking as lazy or resizing
   → fonts.googleapis.com (external)   3.1kB  — consider hosting the font locally
   → style.css                         2.4kB  — CSS looks large; consider purge

   Use --force to ignore this error.
```

fin14 **suggests** optimizations but does not execute them. Fixing is the project's responsibility.

### 7.7 Concurrency Model

fin14 processes pages in **batches of 50** using native `Promise.all` — no p-limit dependency. This stays within macOS file descriptor limits (256 per process) and Linux (1024).

External resource fetches are limited to **10 simultaneous requests per domain**, implemented via a simple semaphore (Map of counters per hostname). No external dependency.

If EMFILE occurs during measurement (error E15), the process automatically retries with a batch of 10 and emits a warning.

### 7.8 Resource Deduplication

The collector resolves all resource URLs to their canonical key before measurement:

- Local resources: absolute filesystem path
- External resources: full URL including query string (hash stripped)

If the same resource appears in multiple categories (e.g., `<link rel="preload" href="hero.jpg">` AND `<img src="hero.jpg">`), it is counted **once** — assigned to the category of its first occurrence in document order. Subsequent occurrences in other categories are silently skipped.

When `--verbose` is active, deduplicated resources are listed:

```
info  hero.jpg already counted as img — skipped preload duplicate
```

## 8. Development Mode (`fin14 dev`)

### 8.1 Features

- Watch output dir with Chokidar — detects when the SSG regenerates files
- Budget report page at `http://localhost:4214` (or next available port)
- Terminal TUI with fixed header of global metrics and dynamic activity zone
- On-demand rebuild via the `R` key in terminal (runs configured `build_command`)
- Server → browser communication via SSE
- Burst detection: changes within a 300ms window treated as a batch
- Adaptive settle delay to avoid measurements on partial output

### 8.2 Typical Usage Flow

```
Terminal 1: hugo server --watch   (or any SSG in watch mode)
Terminal 2: fin14 dev public/     (fin14 watches the output and measures)

  — user saves a content file
  — SSG detects, rebuilds, updates public/
  — Chokidar detects change in public/
  — fin14 waits for settle delay (adaptive)
  — fin14 re-measures affected pages
  — TUI updates in terminal
  — SSE notifies the report page at localhost:4214
```

Alternatively, with `build_command` configured:

```
Terminal 1: fin14 dev             (fin14 manages the build and watch)

  — user presses R in terminal
  — fin14 runs build_command
  — waits for settle delay and output dir to be updated
  — re-measures and updates TUI and report page via SSE
```

### 8.3 Adaptive Settle Delay

The watcher waits for a stabilization period after the last event before starting measurement. The behavior is **adaptive**:

- **Cold session (first 3 builds):** fixed settle delay of 2 seconds. Covers SSGs that take up to 2s to finish writing output.
- **From the 4th build onward:** settle delay = average of previous build times in the session × 1.2 (20% margin). Minimum 200ms, maximum 5s.

The current settle delay is shown in the TUI status line (`settle 340ms`).

**Why not a fixed delay:** SSGs vary widely (Hugo < 100ms; Eleventy with many posts > 1s). A fixed high delay wastes time on fast builds; a fixed low delay produces partial measurements on slow builds.

### 8.4 Report Page (`http://localhost:4214`)

The report page is served by fin14's `dev-server/` on a dedicated port, independent of the SSG server. If port 4214 is busy, the server tries 4215, 4216... until a port is available. The chosen port is shown in the TUI:

```
  fin14  dist/  watching
  report  http://localhost:4215  (4214 in use)
```

There is no script injection into the site pages — zero interference with the SSG development flow.

**Budget map (top of page):**

At the top of the page, above the list, a grid of squares represents all pages on the site — inspired by the GitHub contribution graph. Each square is a page. Colors are fixed:

- Green — within budget (< 13.6kB)
- Yellow — near limit (≥ 13.6kB and ≤ 14.0kB)
- Red — over budget (> 14.0kB)

Clicking a square smoothly scrolls to the corresponding row in the list below, where the user can click to open the side panel with the full page detail.

**Note:** The color zones reflect the 14kB budget only. The conservative 12.2kB threshold (IPv6 heuristic, used by `--strict`) is a CI concern and is not represented in the map colors. In dev mode, pages between 12.2kB and 14kB appear yellow only if they also fall between 13.6kB and 14kB — which is a range coincidence, not a semantic equivalence. The TUI hint layer may mention pages in that interval when relevant.

**Page list (overview):**

Each page appears in one row with:
- Visual status (✓ pass / ⚠ warning / ✗ fail)
- Current size vs. limit (e.g., `9.2 / 14.0 kB`)

The list is sorted by weight (heaviest first) so violations appear at the top.

**Page detail (side panel):**

Clicking a page opens a side panel with the full breakdown by resource type: HTML / CSS / JS / Images / External. External resources are individually identified with their weight and associated warning.

**Updates:**

The page maintains an SSE connection with the server. When the watcher detects a change in the output dir and re-measurement finishes, the server pushes updated data and the page re-renders without a reload.

**History:**

Current snapshot only — no history between measurements. The page always reflects the latest state of the output dir.

### 8.5 Terminal TUI

The TUI is composed of a **fixed header** (always visible) and a **dynamic activity zone** (recent pages). The aesthetic follows the pattern of tools like Claude Code and OpenCode: dark background, dense monospaced typography, semantic colors, light separators, footer with available controls.

**Fixed header (3 lines):**

```
 fin14  dist/  watching           ✓ 38  ⚠ 3  ✗ 7   48 pages
 ─────────────────────────────────────────────────────────────
 top offenders   style.css 8.4kB · hero.jpg 6.1kB · Inter (ext) 3.1kB
 hint            7 pages failing — style.css looks large, check global CSS
```

When the watcher is waiting for the settle delay:

```
 fin14  dist/  watching           ✓ 38  ⚠ 3  ✗ 7   48 pages
 ─────────────────────────────────────────────────────────────
 top offenders   style.css 8.4kB · hero.jpg 6.1kB · Inter (ext) 3.1kB
 settle 340ms    waiting for output to stabilize...
```

- Line 1: tool name, watched output dir, watcher status, global counters (`✓ N ⚠ N ✗ N`), total pages
- Line 2: the 3 heaviest assets across the entire site (not a specific page), with individual sizes
- Line 3: dynamically generated text hint — examples: "7 pages failing — style.css looks large, check global CSS"; "external resource Inter is 3.1kB — consider hosting locally"; "all within budget ✓"

**Activity zone (dynamic):**

Lists the most recently modified pages. Each page takes one line. Resource types with zero weight are omitted. The number of lines displayed is calculated dynamically: `process.stdout.rows - 7` (header + separators + footer).

```
 recent
 ✗  posts/long-post           16.8 / 14.0 kB  +2.8  HTML 3.8  CSS 2.4  Imgs 10.6
 ✓  posts/index                9.2 / 14.0 kB        HTML 4.1  CSS 2.8  Imgs 2.3
 ✓  about/index                7.1 / 14.0 kB        HTML 2.9  CSS 4.2
 ─────────────────────────────────────────────────────────────
 R rebuild · Q quit · ↑↓ navigate · Enter detail
```

When a page is updated, it moves to the top of the activity zone. The oldest ones drop off the bottom.

### 8.6 Burst Mode (batch update)

When multiple files change within a 300ms window — common in full SSG rebuilds — fin14 enters burst mode. This covers both template edits that affect hundreds of pages and full rebuilds triggered by the SSG itself (which often regenerates the entire site regardless of what changed).

**During the burst**, the header hint becomes a progress bar and the activity zone shows only pages with errors as they are detected:

```
 fin14  dist/  rebuilding        ✓ 38  ⚠ 3  ✗ 7   48 pages
 ─────────────────────────────────────────────────────────────
 top offenders   style.css 8.4kB · hero.jpg 6.1kB · Inter (ext) 3.1kB
 hint            updating 347 pages...  [████████████░░░░]  214 / 347
 ─────────────────────────────────────────────────────────────
 errors found
 ✗  posts/long-post            16.8 / 14.0 kB  +2.8  HTML 3.8  CSS 2.4  Imgs 10.6
 ✗  posts/post-b               15.1 / 14.0 kB  +1.1  HTML 3.2  CSS 2.4  Imgs 9.5
```

**When the burst finishes**, if there are no violations, the TUI returns to normal mode. If there are violations:

- If ≥ 30% of pages are red, the hint updates to suggest checking a template or global CSS
- The activity zone shows the paginated list of pages with violations

**Post-burst paginated list:**

When the number of pages with violations exceeds the available height of the activity zone, the list becomes paginated with `←` `→` navigation:

```
 ✗ 89 pages over budget   page 1 / 8   ← →
 ─────────────────────────────────────────────────────────────
 ✗  posts/heaviest-post       18.4 / 14.0 kB  +4.4  HTML 3.1  CSS 2.8  Imgs 12.5
 ✗  posts/second-post         17.9 / 14.0 kB  +3.9  HTML 3.8  CSS 2.4  Imgs 11.7
 ⚠  posts/near-limit          13.7 / 14.0 kB        HTML 4.1  CSS 5.2  Imgs 4.4
```

Sort order: weight descending → recency → filename.

## 9. CI Usage

fin14 is designed to work as a weight linter in CI pipelines:

```yaml
# GitHub Actions example
- name: Build
  run: npm run build

- name: Check page budget
  run: npx fin14 dist/ --strict
```

`--strict` treats as errors: presence of any external resource in budget, pages above 12.2kB (IPv6 heuristic), external fetch failure, and failed `build_command` with stale output available. Exit code 1 on any violation.

## 12. Ecosystem Roadmap

fin14 is the first product of a planned ecosystem. Each phase solves a specific problem and supports the next.

### the14 — Opinionated SSG

Static site generator built on top of fin14. While fin14 is agnostic, the14 is deliberately opinionated: it chooses the stack (Markdown, templates, collections) and applies optimizations that fin14 cannot safely do in an agnostic way — such as CSS purge and critical CSS inlining. Every site generated by the14 is born within budget.

Planned scope: Markdown + frontmatter, template engine, native collections (posts, projects, tags), automatic pagination, hot reload with integrated budget overlay, zero JS by default.

### sam14 — CMS

Content management interface integrated with the14. Solves the problem of those who want to maintain a blog or portfolio without editing Markdown files directly. sam14 relies on the14 for building and fin14 for budget validation — the 14kB limit is enforced even through the visual interface.

Planned scope: web content editor, post and project management, real-time preview with visible budget, integrated publishing.

### Hosting platform (future phase)

If the ecosystem gains sufficient adoption, a hosting platform dedicated to sites within the 14kB limit closes the loop: create, measure, publish — all within the same ecosystem. No server configuration, no concern about compression or CDN.

## 13. Success Criteria (fin14 v1)

### 13.1 Testing Strategy

The implementation must have canonical fixtures and stable snapshots before being considered complete:

- Basic HTML below and above 14,000 bytes
- gzip level 6 and brotli
- Valid `@import`, cycle, and missing import
- `@font-face` with local and external font — first `src:` only
- Eager images, lazy by order, `<picture>` with fallback `src`, and ignored `srcset`
- `preload` and `modulepreload`, with deduplication against same-path img/script
- External fetch with success, timeout, redirect, and 404
- `--strict` failing on external resource, unknown budget, page above 12.2kB, and build warning
- CLI, `audit`, and report UI data snapshots

Acceptance criterion: no section should claim that fin14 measures real network bytes without qualifying the measurement as a deterministic estimate.

### 13.2 Product

- A developer can integrate fin14 into an existing project in under 5 minutes
- fin14 works correctly with Hugo, Eleventy, and Astro without SSG-specific configuration
- The report page updates in under 500ms after the SSG regenerates a file
- `fin14 dist/` on a site with 100 pages ≤14kB completes in under 5 seconds

## Appendix B — Error Taxonomy

### Category A — Input errors

Exit 1. Clear message. No measurement.

| ID | Condition | Example message |
|---|---|---|
| E01 | `output_dir` does not exist | `error  dist/ not found` |
| E02 | `output_dir` has no `.html` files | `error  no HTML files found in dist/` |
| E03 | `fin14.toml` invalid (parse error) | `error  fin14.toml: parse error at line 4` |
| E04 | `fin14.toml` with unknown field | `error  fin14.toml: unknown field 'cache_ttl'` |
| E05 | `.html` file passed to `audit` does not exist | `error  file not found: posts/x.html` |

### Category B — Measurement errors

Warning emitted. Process continues. Missing local resources are excluded from budget; external failures mark budget as unknown.

| ID | Condition | Behavior |
|---|---|---|
| E06 | CSS referenced in HTML not found on disk | `warn  style.css not found — excluded from budget` |
| E07 | JS referenced in HTML not found on disk | same |
| E08 | Image referenced not found on disk | same |
| E09 | External resource fetch failed (timeout / redirect / 4xx / 5xx) | `warn  fonts.googleapis.com: fetch failed — budget unknown`; error in `--strict` |
| E10 | `@import` references a file not found on disk | `warn  @import 'tokens.css' not found — excluded` |
| E11 | Cycle in `@import` (A imports B imports A) | `warn  cycle detected in @import: base.css → tokens.css → base.css` |
| E18 | Known resource outside v1 matrix found in `--verbose` | `warn  background-image in style.css is outside v1 matrix — ignored` |

### Category C — Budget errors

Exit 1 by default. Exit 0 with `--force`.

| ID | Condition | Behavior |
|---|---|---|
| E12 | Page > 14kB | error; exit 1 |
| E13 | Page > 12.2kB and ≤ 14kB | warning; error in `--strict` |
| E14 | External resource present in budget | warning; error in `--strict` |
| E19 | Unknown budget from external fetch or failed build | warning; error in `--strict` |

### Category D — Runtime errors

| ID | Condition | Behavior |
|---|---|---|
| E15 | EMFILE (too many open files) | automatic retry with batch of 10; warning emitted |
| E16 | Port 4214 busy (dev mode) | tries next available port; TUI reports chosen port |
| E17 | `build_command` failed (exit ≠ 0) | log stderr + continue if `output_dir` exists; marks budget as unknown |
